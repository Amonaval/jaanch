# M13.5 — Profile + Secure Persistence Architecture v1

Status: **ENGINEERING IMPLEMENTED — OWNER PERSISTENCE/PRIVACY REVIEW REQUIRED**  
Effort: **High**

## Objective

Introduce a storage-vendor-independent persistence boundary for sensitive Jaanch health history without prematurely enabling cloud storage.

M13.5 does **not** turn the prototype into a production medical-record system. It creates the contracts required so identity, consent, retention, encryption expectations, deletion, export and future cross-device sync are explicit rather than accidental.

## What changed

### 1. Versioned persistence envelope

New protocol:

```text
JAANCH-PERSISTENCE-1.0
```

Implemented in:

```text
packages/core/src/persistence.ts
```

The persistence document contains:
- profile identity and owner type;
- consent state and policy version;
- retention policy;
- security metadata;
- revision/sync metadata;
- immutable longitudinal history.

Existing application callers continue to use `encodeLongitudinalHistory(...)` / `decodeLongitudinalHistory(...)`. Encoding now writes the M13.5 envelope; decoding accepts both the new envelope and the legacy `JAANCH-HISTORY-1.0` payload. This keeps web/mobile behavior compatible while moving storage semantics into a versioned contract.

### 2. Profile ownership boundary

Two owner modes exist:

```text
local_device
  → current alpha behavior
  → no authenticated cloud ownership

authenticated
  → stable auth subject + provider
  → required before any remote persistence can be eligible
```

Authentication credentials/tokens are deliberately **not** part of the persisted health document.

### 3. Consent model

Persistence records:
- local-history consent basis;
- cloud-sync consent state: `granted`, `not_granted`, or `revoked`;
- policy version;
- consent timestamp.

Cloud sync fails closed unless consent is explicitly `granted`.

Consent revocation immediately moves the document back to `local_only` and disables the remote-sync eligibility flag.

### 4. Security decisions are explicit

Supported security metadata values:

```text
application_storage_unencrypted
platform_protected_encrypted
server_encrypted
```

Current runtime truth:
- web history remains browser `localStorage`;
- mobile history remains AsyncStorage;
- Jaanch does not claim application-layer encryption for those current stores;
- therefore the current runtime is explicitly marked `application_storage_unencrypted` and `local_only`.

Remote persistence is blocked unless all of these are true:
1. authenticated profile ownership;
2. explicit cloud-sync consent;
3. TLS-required transport;
4. server-side encryption-at-rest metadata;
5. document state resolves to `sync_eligible`.

This prevents local JSON portability from silently becoming permission to upload health data.

### 5. Storage-vendor-independent backend port

`SecurePersistencePort` defines the future remote boundary:

```text
load(authenticated scope)
save(authenticated scope, encoded document, expected revision)
delete(authenticated scope, deletion tombstone, expected revision)
```

No Supabase/Firebase/AWS-specific type exists in the clinical core.

A future backend adapter must sit outside deterministic clinical semantics and satisfy this contract.

### 6. Migration compatibility

M13.5 keeps reading legacy:

```text
JAANCH-HISTORY-1.0
```

and provides an explicit legacy migration helper that records:

```text
basis = legacy_local_migration
remoteSyncAllowed = false
```

Legacy history is therefore not interpreted as cloud consent.

### 7. Retention semantics

Current v1 policy:

```text
mode = until_user_deletes
maxSnapshots = 20
```

The persistence normalizer enforces the configured snapshot cap while retaining newest-first immutable history semantics.

This is a product policy contract, not a claim that OS/browser storage can never be cleared externally.

### 8. Cross-device merge rules

`mergePersistenceDocuments(...)` provides deterministic future sync behavior.

Rules:
- both documents must independently pass the remote-persistence gate;
- profile ID and authenticated owner must match;
- snapshot IDs are immutable;
- identical snapshot IDs with different payloads are treated as a conflict, not silently overwritten;
- duplicate immutable snapshots are deduplicated;
- merged history respects the stricter retention cap;
- revision advances monotonically from the participating remote documents.

No last-write-wins overwrite of conflicting medical history is allowed.

### 9. Delete propagation

New protocol:

```text
JAANCH-DELETION-1.0
```

Deletion propagation uses a minimal tombstone containing:
- profile ID;
- owner identity boundary;
- deletion timestamp;
- next revision.

The tombstone contains **no health history**.

This is intended to prevent a stale device from casually resurrecting deleted cloud data when a future sync backend is connected.

### 10. Data export semantics

New export protocol:

```text
JAANCH-DATA-EXPORT-1.0
```

The user data export includes:
- owned profile identity metadata;
- consent record;
- retention policy;
- longitudinal health history.

It deliberately excludes backend security configuration and credentials.

This is separate from `JAANCH-PROFILE-1.0`:
- `JAANCH-PROFILE-1.0` = runnable/testing portability that reruns the current engine;
- `JAANCH-DATA-EXPORT-1.0` = owned persisted-data export semantics.

## Evidence-integrity preservation

Persisted snapshots are normalized on decode and private `__m134_*` derived fields are stripped again.

M13.5 therefore does not weaken the M13.4 rule that broader clinical evidence must be rebuilt only through the trusted measurement materialization path.

## Verification

New suite:

```text
packages/core/src/verificationPersistence.ts
```

Coverage includes:
- new persistence-envelope encoding;
- backward-compatible legacy history decoding;
- legacy migration stays local-only;
- truthful current local security metadata;
- local-device owner cannot use remote persistence;
- authenticated owner + consent + TLS/server encryption can cross the remote gate;
- cloud-sync consent revocation fails closed;
- same-owner cross-device merge deduplicates history;
- cross-owner merge is rejected;
- forged private M13.4 fields are stripped during persisted-data decode;
- deletion tombstone contains no health history;
- owned-data export excludes backend security/credential material.

The suite is wired into `npm run verify` through `verifyCli.ts`.

## Current runtime state after M13.5

What is implemented now:
- local persistence envelope;
- identity/consent/retention/security/sync contracts;
- migration compatibility;
- remote eligibility gate;
- backend port;
- conflict-safe merge semantics;
- deletion tombstone semantics;
- data-export semantics;
- deterministic verification.

What remains intentionally **not connected**:
- real sign-in/account provider;
- remote database;
- live backup/sync;
- device-to-device continuity;
- production key management;
- application-layer encryption of current browser localStorage/AsyncStorage;
- production privacy policy / legal consent UX;
- production telemetry/crash-data policy.

Those are deployment/pilot choices, not reasons to couple storage into the clinical core.

## Owner review gate

Before calling persistence pilot-ready, verify:
1. current local-only status is clear and not presented as encrypted medical-record storage;
2. legacy local check-ins still load after upgrading;
3. save/import/report flows continue to round-trip history;
4. profile JSON portability remains distinct from account/cloud sync;
5. delete/export wording is understandable;
6. a future backend choice does not weaken authenticated ownership, consent, encryption or revision checks.

## Non-goals / anti-overbuilding

M13.5 does not add a backend vendor merely to demonstrate cloud storage.

It also does not:
- store auth tokens in health records;
- infer cloud consent from profile import/export;
- allow anonymous remote health history;
- silently merge conflicting immutable snapshots;
- claim current localStorage/AsyncStorage is encrypted by Jaanch;
- alter deterministic clinical rules based on persistence technology.
