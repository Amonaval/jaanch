# M13.3 — Clinical Evidence Capture v2 / Report UX

Status: **ENGINEERING IMPLEMENTED — OWNER EVIDENCE-INGESTION RETEST REQUIRED**  
Effort: **High**

## Goal
Make report/result capture materially easier without weakening evidence integrity or expanding clinical interpretation by accident.

## Implemented

### Shared core
- provider-neutral `ReportEvidenceCandidate` contract;
- report-level provenance: report ID, filename, asset kind, MIME type/size, import time and extraction method/provider metadata;
- deterministic text/OCR candidate extraction for common captured markers;
- marker normalization for HbA1c, B12, Vitamin D, glucose, lipids, hemoglobin, ferritin, TSH and blood pressure;
- extraction confidence and clarification/issues surfaced explicitly;
- candidate values are inert until explicit user review/confirmation;
- supported HbA1c/B12 candidates still pass through the existing unit/date/verification/freshness/plausibility gates;
- unsupported markers become `recorded_unassessed` after confirmation and cannot silently influence findings;
- exact duplicate replacement plus existing latest-result semantics for distinct/newer results;
- report provenance retained on confirmed evidence through normalization;
- batch workflow applies reviewed report candidates to one reassessed immutable snapshot based on the latest saved check-in.

### Web
- dedicated **Import lab report** surface without rewriting the existing assessment App;
- browser PDF/image/text file picker for source provenance;
- pasted report text/OCR extraction;
- editable value, unit, collection date and reference range;
- per-candidate confidence, issues, review/confirm and ignore controls;
- reviewed candidates are applied together to the latest saved check-in.

### Mobile
- dedicated report-import surface wrapping the existing Expo assessment App;
- `expo-document-picker` for PDF/image/text attachment;
- same review/confirmation semantics as web;
- returning to assessment remounts the existing App so the newly persisted longitudinal check-in is reloaded.

## Important alpha limitation
M13.3 does **not** claim trustworthy OCR/PDF parsing from raw document bytes. PDF/image selection currently preserves source provenance; the user pastes report text or OCR output for deterministic candidate parsing. This is intentional until a privacy/quality-reviewed extraction provider is selected.

The core exposes a provider-neutral extraction contract so a future OCR/document service can produce candidates without being allowed to bypass confirmation or clinical eligibility gates.

## Safety boundaries preserved
- report text never becomes a diagnosis automatically;
- extraction never equals evidence eligibility;
- no prescription or treatment recommendation is generated from report prose;
- capture breadth still does not authorize interpretation breadth;
- urgent/safety/applicability and deterministic evidence rules remain authoritative;
- report import requires an existing saved baseline so reassessment does not fabricate missing profile context.

## Verification added
Deterministic cases cover:
- extraction creates candidates only;
- marker normalization;
- explicit confirmation boundary;
- report provenance survives normalization;
- supported-lab eligibility still uses normal gates;
- unsupported Vitamin D remains recorded/unassessed;
- missing collection date blocks supported-lab confirmation;
- exact duplicates are deduplicated;
- newer distinct results remain in history and win latest-result selection;
- mixed reviewed candidates create one reassessed snapshot;
- unknown markers surface low-confidence/unsupported warnings.

## Owner retest gate
Before treating M13.3 as product-validated, confirm:
1. attach a PDF/image and verify source provenance is visible;
2. extract HbA1c/B12 plus at least one unsupported result;
3. edit an intentionally wrong value/unit/date before review;
4. verify extraction alone changes nothing;
5. verify HbA1c/B12 only become eligible after explicit review and normal validation;
6. verify Vitamin D/lipids remain recorded/unassessed;
7. import an exact duplicate and verify it is not double-counted;
8. import a newer distinct result and verify longitudinal/latest semantics;
9. compare web/mobile meaning and ordering;
10. verify the flow clearly requires a saved baseline rather than inventing missing profile context.

Any trust/result-quality defect discovered in owner testing remains higher priority than roadmap expansion.
