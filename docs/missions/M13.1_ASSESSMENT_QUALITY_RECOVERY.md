# M13.1 — Assessment Quality Recovery + Block UX v2

Effort: **HIGH**
Status: **NEXT / RELEASE-BLOCKING FOR ALPHA**
Origin: first hands-on owner review after M13

## Why this mission changed

The first real product test showed that Jaanch is currently an engineering prototype with an auditable core, but not yet a credible health-assessment experience.

Observed problems:

- UI is too plain / engineering-oriented;
- the flow is one question → Next → one question → Next instead of grouped blocks;
- Back/Next navigation can lose a dynamically planned question;
- going back does not reliably return to the exact previous question/block state;
- height and waist accept only canonical metric units rather than user-friendly cm/ft-in/inches;
- diagnosed-condition choices are too narrow and lack a useful manual path;
- medicine capture is too shallow; a user taking a cholesterol medicine cannot adequately describe it;
- current-concern choices are too narrow and lack manual input;
- physical activity treats exercise days as the main signal and fails to represent ordinary walking well;
- exercise quality/intensity/type is not captured;
- known lab capture is biased to markers Jaanch already interprets (HbA1c/B12), so known Vitamin D and other values can be lost;
- the detailed context available for future AI/review is therefore incomplete;
- the original 10–20 master → adaptive 20–50+ follow-up vision has been compressed too aggressively.

This mission is not cosmetic. **Input quality determines output quality.**

---

# Mission objective

Rebuild the assessment intake into a credible, mobile-first evidence-capture experience while preserving the deterministic safety/evidence architecture.

The user should feel that Jaanch can accurately capture their health context even when Jaanch cannot yet interpret every fact.

---

# A. Block-based assessment flow

Replace one-question-per-screen as the default experience.

Target top-level blocks:

1. About you & measurements
2. Health history & medicines
3. Current health & symptoms
4. Lifestyle
5. Tests / known measurements
6. Adaptive follow-ups when activated

Guidelines:

- a block typically contains ~3–8 related fields;
- inline conditional fields can reveal within a block;
- one Continue action per block, not per tiny field;
- urgent safety questions may interrupt immediately;
- adaptive follow-ups appear as grouped blocks;
- desktop may show denser layouts; mobile remains the primary interaction model.

## Acceptance criteria

- Typical low-complexity user reaches results in roughly 4–6 top-level navigations.
- Higher-complexity users may receive more adaptive blocks, but not dozens of tiny Next interactions.
- Progress is section-based, e.g. `About you • History • Lifestyle • Tests • Follow-ups`, not a fluctuating question count.

---

# B. Navigation integrity

Current dynamic planner navigation is not acceptable for alpha.

Implement stable visited-flow state separate from the dynamic eligibility planner.

Required concepts:

- `AssessmentBlock` with stable block ID;
- visited block stack/history;
- current block cursor;
- forward visited history where appropriate;
- planner revision/version;
- invalidated downstream field tracking;
- explicit edit/deep-link target.

## Acceptance criteria

- Back returns to the exact block the user previously saw.
- Next after Back returns to the next visited block unless the earlier edit legitimately changes the plan.
- If the plan changes, the UI explicitly says what new/removed follow-up changed.
- Previously entered answers do not silently disappear.
- Editing an earlier answer can invalidate downstream values, but invalidation must be deterministic, visible and test-covered.
- Red-flag interruption preserves the prior navigation state.
- Add a golden regression for the exact owner-observed bug: visit adaptive question → go Back → go forward → the adaptive question must still be reachable/preserved when still eligible.

---

# C. Richer evidence/question bank

Restore the original adaptive-assessment ambition.

Target bank size for this stage:

- ~15–25 high-information master fields/questions;
- ~50–100 potential evidence fields/follow-ups across supported capture categories;
- typical user sees only relevant fields through 4–6 main blocks + adaptive blocks.

This number is a coverage target, **not a goal to interrogate every user**.

Categories to expand:

- demographics/context;
- anthropometrics;
- diagnosed conditions;
- medication/supplement context;
- family history;
- current concerns/symptoms;
- diet/nutrition;
- walking + physical activity;
- sleep;
- tobacco/alcohol where in scope;
- known blood pressure;
- known labs/measurements;
- safety/special-population context;
- optional additional context.

Do not add deterministic disease conclusions merely because capture becomes broader.

---

# D. Measurements & units

## Height
UI choices:
- cm;
- ft + in.

Store canonical `heightCm` internally.

## Waist
UI choices:
- cm;
- inches.

Store canonical `waistCm` internally.

## Weight
UI choices:
- kg;
- lb if practical in this mission.

Store canonical `weightKg` internally.

Acceptance:
- unit can be changed without corrupting the stored value;
- conversions have deterministic tests;
- visible entry always shows the selected unit.

---

# E. Diagnosed conditions

Replace the current seven-item flat list with a broader capture model.

At minimum support categories/chips for common areas such as:

- diabetes / prediabetes;
- hypertension;
- high cholesterol / lipid disorder;
- heart / vascular disease;
- kidney disease;
- liver disease;
- thyroid disease;
- asthma/respiratory disease;
- anemia/iron deficiency where known;
- vitamin deficiency where known;
- gastrointestinal conditions;
- neurological conditions;
- mental-health diagnoses where user chooses to capture them;
- cancer/current major disease context where relevant to safety;
- other.

The exact catalogue should be reviewed for product usefulness and safety; it does not imply interpretation support.

Required:
- searchable/expandable choices rather than an enormous permanent list;
- mutually-exclusive `None / not diagnosed`;
- `Other` manual condition input;
- custom conditions retained as user-reported context;
- unsupported conditions clearly distinguished from interpreted findings.

---

# F. Medicines & supplements

Replace count/category-only capture with entries.

Minimum medicine entry:

- name/manual text;
- optional category;
- reason/purpose if known;
- optional dose/frequency later if the user wants detail.

Examples the UI must support:

- user enters a statin/cholesterol medicine by name;
- user enters a medicine not in the catalogue;
- user records multiple medicines;
- user can edit/delete an entry.

Supplements likewise need named/manual entries in addition to quick options.

Do not infer a diagnosis solely from a medicine name without an explicit reviewed mapping.

---

# G. Current concerns / symptoms

Expand beyond fatigue / sleep / tingling / chest pain / thirst.

Use a layered model:

- common concern chips;
- optional category expansion;
- `Other concern`;
- manual/free-text details.

Potential high-level categories include:

- energy/fatigue;
- sleep;
- pain;
- breathing;
- heart/chest symptoms;
- gastrointestinal symptoms;
- urinary symptoms;
- neurological symptoms;
- skin/hair concerns;
- weight/appetite changes;
- mood/stress when in scope;
- other.

Structured red-flag patterns remain explicit/deterministic. Free text is preserved as context but does not automatically trigger rules.

---

# H. Walking & physical activity

Replace the current single `activityDays` question with a richer activity profile.

Capture at least:

## Walking
- does the user walk regularly?;
- days/week;
- typical minutes/day or session;
- steps/day when known;
- perceived pace/intensity where useful.

## Structured activity
- strength/resistance;
- running/jogging;
- cycling;
- swimming;
- sport;
- yoga/mobility;
- gym/cardio;
- other/manual.

For activities:
- days/week;
- minutes/session;
- intensity: light/moderate/vigorous.

Derive an activity summary while preserving raw components.

Acceptance:
- daily walkers are not classified as inactive solely because they did not select formal exercise.

---

# I. Known measurements / labs: capture broader than interpretation

The intake must ask what the user already knows, not only what current rules happen to support.

Expand normalized capture catalogue to at least:

- HbA1c;
- fasting/random glucose where appropriate;
- Vitamin B12;
- **Vitamin D**;
- total cholesterol;
- LDL;
- HDL;
- triglycerides;
- hemoglobin;
- ferritin/iron where known;
- TSH;
- blood pressure;
- other/manual test/measurement.

For every known numeric lab/measurement capture:

- value;
- unit;
- collection/measurement date when known;
- source;
- user verification;
- optional report reference range.

Important behavior:

- Jaanch may capture Vitamin D even before a deterministic Vitamin-D interpretation rule exists.
- Unsupported captured markers appear under `Recorded context — not yet assessed by Jaanch`.
- Only markers with sourced/applicable deterministic rules influence deterministic findings.
- Future AI packet can include selected unassessed evidence only through explicit minimization/consent policy.

---

# J. Family history

The current diabetes-only family-history model is too narrow for a general preventive assessment.

Add structured capture for a limited high-value set such as:

- diabetes;
- premature cardiovascular disease;
- hypertension;
- lipid disorder;
- selected cancers where later product scope justifies it;
- thyroid/autoimmune or other high-value areas only when there is a clear product use;
- other/manual family-history context.

Do not expand endlessly; capture should be useful or retained as unassessed context.

---

# K. Free-form / Other evidence model

Introduce a shared capture type for facts Jaanch cannot fully structure yet.

Suggested states:

- `structured`;
- `user_reported_unstructured`;
- `recorded_unassessed`;
- `needs_clarification`.

Manual facts must survive save/retest/history.

They should be visible in a detailed context section without being confused with deterministic findings.

---

# L. UI redesign direction

The current UI should not just be restyled; its information architecture changes with block flow.

Required:

- attractive mobile-first cards/sections;
- concise header and block purpose;
- block progress/navigation;
- chips/search/manual entry patterns;
- selected-item summaries;
- clear units;
- inline optional detail;
- fewer borders/developer-looking blocks;
- results use stronger hierarchy and whitespace;
- technical rule IDs/sources live under `Why / Evidence / Clinical details`, not dominate the main surface.

Do not spend effort on decorative animation before navigation/capture quality is correct.

---

# M. Result-quality / trust gate

M13.1 is successful only if the owner can complete realistic profiles and say:

> Jaanch captured the material facts I expected it to know.

Required hands-on scenarios:

1. generally healthy adult;
2. vegetarian with low B12 + low Vitamin D history;
3. user on cholesterol and blood-pressure medication;
4. daily walker with little formal exercise;
5. user with an unlisted diagnosed condition and unlisted current concern;
6. metabolic-risk profile with known HbA1c/lipids;
7. user who edits an earlier block after adaptive follow-ups were created;
8. urgent chest-pain path;
9. repeat check-in preserving manual/custom facts.

If these profiles cannot be faithfully represented, do not proceed to AI value evaluation or broader release work.

---

# Verification requirements

Add deterministic tests for:

- unit conversions;
- block eligibility;
- block back/forward history;
- adaptive block preservation after Back;
- visible downstream invalidation;
- custom/manual condition persistence;
- medicine entries and purposes;
- walking/activity aggregation;
- Vitamin-D/unassessed lab preservation;
- `None` exclusivity with expanded lists;
- web/mobile shared capture schema;
- snapshot persistence of custom/manual facts.

---

# Non-goals

- do not diagnose every captured condition;
- do not add treatment algorithms for Vitamin D/lipids/thyroid merely to match capture breadth;
- do not use free text as unreviewed medical rules;
- do not make AI responsible for repairing incomplete data collection;
- do not build cloud persistence before the intake model stabilizes.

---

# Exit criteria

M13.1 closes only when:

1. assessment is block-based;
2. navigation regression is fixed and covered;
3. measurements have human-friendly units;
4. conditions/concerns/medicines/supplements support Other/manual input;
5. walking + richer activity are captured;
6. known lab capture includes Vitamin D and broader common evidence;
7. unsupported evidence is retained as recorded/unassessed context;
8. results/detail preserve richer context;
9. UI is materially more consumer-ready;
10. owner hands-on review passes the trust gate above.

Recommended commit budget may be raised to **3–4 commits for this mission** because it is a corrective product-quality mission spanning shared schema, planner/navigation, both UIs and verification. Do not artificially compress it into unsafe/opaque changes merely to hit the normal 1–2 commit guideline.
