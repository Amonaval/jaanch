# M13.6 — Consumer Value Reset: Health Intelligence Brief + Smart Recheck

Status: **ENGINEERING IMPLEMENTED — OWNER VALUE / UX RETEST REQUIRED**  
Effort: **High**  
Origin: Strategic Review 3

## Objective

Make the existing supported Jaanch scenarios feel materially more useful without expanding broad clinical scope.

Success requires two things:
1. a user understands the result within seconds;
2. a returning user can continue without rebuilding established history.

## Implemented scope

### Health Intelligence Brief

New core module:

```text
packages/core/src/healthBrief.ts
```

The result now compresses supported findings into at most three deterministic health priorities/themes.

Current bounded synthesis:

```text
cardiometabolic
  MET-001 + CV-BP-001 + CV-LIPID-001

blood-nutrition
  NUT-001 + NUT-IRON-001

thyroid
  MET-THYROID-001

sleep
  SLP-001
```

Urgent safety stays separate and dominant.

Each visible priority answers:
- what Jaanch sees;
- why it matters;
- supporting evidence;
- next best action;
- what can wait;
- what evidence would most change the view.

Low-risk profiles may show zero priority cards. Jaanch should stay quiet rather than manufacture generic wellness filler.

### Result hierarchy reset

New web component:

```text
apps/web/src/HealthBriefPanel.tsx
```

First layer:
- headline;
- best next action;
- 0–3 priorities;
- why each matters;
- decision-changing evidence;
- optional evidence chain;
- change since previous check-in.

Demoted behind evidence/clinical details:
- evidence completeness;
- interpreted-area counts;
- mapped uncertainty counts;
- raw captured context;
- detailed findings;
- governance/maturity;
- technical HAP JSON.

Traceability remains available; it no longer defines the first screen.

### Smart Recheck

New core module:

```text
packages/core/src/recheck.ts
```

`createSmartRecheckDraft(snapshot)`:
- restores sanitized answers;
- restores captured history/medicines/supplements/family context;
- restores recorded measurements;
- converts normalized HbA1c/B12 snapshots back to raw runnable lab records;
- does not trust old freshness/eligibility state;
- strips internal `__m134_*` fields.

Web quick recheck:
- starts from the latest saved check-in;
- initially asks likely-to-change facts such as weight/waist/current concerns/sleep/walking;
- allows focused editing when history/medicines/tests/lifestyle changed;
- shows deterministic change summary before saving.

### User-owned portable Jaanch history

M13.6 now also makes continuity a consumer feature without requiring accounts/backend storage.

Primary navigation includes:

```text
My Jaanch file
```

The existing `JAANCH-PROFILE-1.0` format is reused rather than creating a second portable format.

Export flow:

```text
saved local history
→ profileBundleFromHistory(...)
→ jaanch-health-YYYY-MM-DD.json
→ user keeps the file
```

Import flow:

```text
user selects previous Jaanch JSON
→ decode + validate profile bundle
→ restore included longitudinal history locally
→ if old bundle has no history, rerun its runnable draft once
→ main app reloads
→ Quick Recheck uses restored latest snapshot
```

No name is required by Jaanch and no Jaanch-hosted health database/account is required for this workflow.

Privacy statement must remain precise:
- this removes Jaanch backend custody from the continuity path;
- it does **not** make the exported health file non-sensitive;
- free-text fields can contain identifying/sensitive information entered by the user;
- email/storage providers chosen by the user are outside Jaanch's custody/control.

A simple user routine is encouraged:
1. finish/update Jaanch;
2. download My Jaanch file;
3. keep it in a folder/storage the user controls;
4. optionally email it to themselves if comfortable with their email provider storing health information;
5. upload it next time;
6. update only what changed;
7. export the refreshed file again.

### Established facts

Stable facts should not be repeatedly asked merely because a browser/session changed.

Age caveat: an earlier integer age plus timestamp does not identify the person's birthday, so Jaanch must not silently claim an exact newly-derived age. Carry the prior value as a default and ask for correction/confirmation only when materially stale or clinically relevant.

### Consumer navigation

Primary:
- Latest Health Brief (when history exists);
- My Jaanch file;
- Import lab report.

Advanced / experimental:
- AI second opinion;
- Profiles & test mocks.

AI v2 remains optional and cannot define the Health Brief.

## Deterministic verification

New suite:

```text
packages/core/src/verificationConsumerValue.ts
```

Checks include:
- max three priorities;
- quiet low-risk behavior;
- no low-risk filler/missing-test promotion;
- cardiometabolic clustering;
- B12 + iron/anaemia clustering;
- no therapeutic-dose invention;
- thyroid dominance with medication-change boundary;
- severe TG dominance without false emergency semantics;
- Smart Recheck stable context preservation;
- normalized lab -> raw rerun boundary;
- internal M13.4 evidence stripping;
- deterministic brief repeatability.

Existing profile verification continues to cover versioned profile JSON import/export and history-preserving export.

## Non-goals preserved

M13.6 does not add:
- broad new clinical domains;
- more AI contracts/agents;
- cloud/auth/backend;
- mobile parity;
- production/store hardening;
- Rule Studio;
- MCP/ChatGPT;
- autonomous treatment changes.

## Known limitations

1. Theme synthesis is bounded, not a general medical ontology.
2. Quick Recheck optimizes routine changes; major history/medicine/test changes route to fuller editing.
3. Exact age cannot be safely advanced from prior integer age + timestamp alone without DOB.
4. Report-first flow is still too cumbersome; M13.7 remains conditional next work.
5. Mobile parity remains intentionally frozen.
6. Portable JSON is not encrypted by Jaanch and should be treated as a personal health document.
7. No claim is made that M13.6 passed the subjective wow gate without hands-on owner testing.

## Owner exit gate

### Five mocks
Within ~10 seconds, answer:
1. What is the top concern?
2. Why?
3. What happens next?
4. What evidence would most change the view?

### Portable repeat-use flow
1. Save a check-in.
2. Download My Jaanch file.
3. Import it in a clean/test session.
4. Confirm history is restored.
5. Confirm Quick Recheck reuses established facts.
6. Confirm the change preview is useful.
7. Export the updated file again.

## Mission decision

**Engineering implementation is complete. Consumer-value validation remains open.**

If hands-on testing still feels merely “okay”, correct M13.6 first.

If it clearly improves value density, the conditional next mission is:

**M13.7 — Report-First Intelligence + Friction Reduction — High**

with user-owned Jaanch history remaining the continuity mechanism unless real product need justifies something else.
